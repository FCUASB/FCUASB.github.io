# 大呂的音樂，未完待續：網站規格書

文件版本：草案 0.1｜整理日期：2026-10-22（臺灣）

適用讀者：委託人、內容校對者、投稿審核者、設計及工程人員。

本文件整理目前的考慮與決定，供大家確認網站要做到什麼、哪些事情還需要討論。**規格寫在這裡，不代表功能已完成；草案中的待確認項目也不代表已獲同意。**

## 1. 先讀這一頁

網站希望讓親友認識大呂、閱讀與分享回憶，並查閱有來源可核對的音樂生涯、演出及作品資料。延續目前設計，逐步補上共用投稿與管理能力，不重新設計整個網站。

| 狀態 | 目前結論 | 對使用者的意思 |
| --- | --- | --- |
| 現有功能 | 可以瀏覽網站內建的公開資料 | 親友可閱讀回憶、音樂足跡、演出及作品資料 |
| 現有限制 | 投稿、補充及檢舉只存在自己的瀏覽器 | 其他人與管理者目前收不到；換裝置也看不到 |
| 已決定方向 | 採用 Supabase 作為主要後端 | 未來用來處理共用資料、附件與管理者身分；尚未串接 |
| 已記錄規劃 | 保留 GitHub Pages 前端，Google Drive 作為原始素材歸檔目的地 | 網站呈現沿用現有做法；歸檔仍需另外建置及授權 |
| 待確認 | 誰審核、何時公開、誰負責帳號與費用 | 需委託人指定，工程端不能自行決定 |

以下為現有功能及維護界線；後續修改應持續驗證，不能只因文件列出便視為每項已實測。

| 項目 | 要保留的規格 | 驗收時看什麼 |
| --- | --- | --- |
| 整體外觀 | 保留原版設計及目前首頁；根目錄與 `/handoff-v1.1/` 由同一來源產生 | 兩個入口顯示一致內容 |
| 手機版 | 肖像比例正常、完整照片可閱讀；保留已修正的日期拆行及表單彈窗寬度 | 360、390、430px 與桌面沒有不應有的橫向溢出 |
| 回憶文字 | 超過 100 個可見字元才收合，可展開及收回；組合 emoji 算一個字元 | 一般文字及 emoji 的字數、剩餘字數與展開結果正確 |

| 投稿附件 | 每則最多 10 個，可分次加入及移除 | 第 11 個不能加入，移除後可再加入；檔案大小限制另待確認 |

| 搜尋與瀏覽 | 保留搜尋、年代排序、相簿翻頁及作品跨場次索引 | 修改相關功能時逐項操作確認 |
| 內容來源 | 保留來源與不確定註記，不捏造回憶、署名、曲目或生涯細節 | 每筆修訂可回查來源；取消、原定或待核資料不寫成確定演出 |

## 4. 共用投稿的目標與界線

### 現在的狀態

新增回憶、照片、影片、音樂會、曲目補充與回報草稿，目前保存於投稿者自己的瀏覽器。表單送出前後都應清楚說明保存位置，不能讓人以為已公開或已送達管理者。喜歡等互動也不能在未驗證前宣稱是跨訪客共用結果。

### 已決定的方向

依 [後端決策紀錄 0001](decisions/0001-supabase-backend.md)，採用 Supabase，考量是同時支援投稿互動，以及演出、曲目、人物、來源與校訂之間的關係。決策紀錄曾比較 Firebase 與 Supabase；Google Drive 歸檔不限定使用哪一個後端。

先保留現有網站內容與設計，優先處理新投稿，再依需求逐步導入音樂史資料。**既有瀏覽器內的內容不得自動上傳。**如未來要提供匯入，需另訂使用者明確選擇的流程。

### 規劃流程，尚待公開規則確認

1. 訪客填寫文字及附件，送出前看見資料用途與保存說明。
2. 網站確認共用收件成功後，才顯示已收到；失敗時不可顯示成功。
3. 由指定人員處理投稿；待審內容及附件不能被未授權者讀取。
4. 若採核准後公開，只有核准內容供其他訪客閱讀。是否所有投稿都需先審，仍待決定。
5. 原始素材依確認的規則歸檔至 Google Drive；歸檔失敗需可辨識及重試，重試不能重複建檔。

以上是規劃及驗收方向，尚未建置服務、管理後台或正式收件流程。刪除、退回、修改及檢舉處理方式亦需另行確認。

## 5. 內容、權利與管理責任

- 網路上可閱讀或已標示來源，不等於取得轉載授權；照片、人物同意與素材權利由內容負責人確認。
- 保留資料差異及待核註記；校對者提出修正時，需保留修正依據。
- 管理者帳號需能識別身分，並限制只有適當人員可審核或管理資料；具體角色權限待確認。
- 不把密碼、管理金鑰、個資或測試投稿放入公開程式庫。
- 資料庫與照片、影片都需要備份及實際還原驗證；網站畫面退回舊版不能還原雲端資料。

## 6. 尚待決定的事項

所有負責人尚待委託人指定，下列項目沒有因本規格書而自動核定。

| 議題 | 需要確認的問題 | 影響 |
| --- | --- | --- |
| 投稿與公開（PRODUCT-01） | 誰審核？哪些內容可公開？如何退回、修改、刪除及處理檢舉？ | 正式收件流程與管理工作量 |
| 帳號與費用（BACKEND-01） | Supabase 與 Drive 歸誰管理？預算、容量、付費核准人是誰？ | 服務能否長期維運 |
| 附件與防濫用 | 允許哪些格式、單檔多大、保留多久？如何限制惡意或大量投稿？ | 使用體驗、費用及維護負擔 |
| Drive 歸檔 | 放在哪個資料夾？誰可存取？何時歸檔？失敗由誰處理？ | 素材保存及存取權限 |
| 備份與還原 | 誰執行、多久一次、保存多久、可接受遺失多少資料及停機多久？ | 資料復原能力 |
| 導覽（UI-03） | 各分頁設新增按鈕，或使用統一補充入口？ | 投稿入口與操作路徑 |
| 首頁重複內容（UI-04） | 哪些區域重複？精選顯示幾筆？完整內容入口在哪？ | 首頁篇幅及閱讀順序 |
| 提示文字（UI-02、UI-06） | 如何清楚且親切地說明本機保存、統計及等待補充？ | 訪客能否理解資料狀態 |
| 曲名與影片（MEDIA-01、02） | 曲名需何種正式資料佐證？Allen 所指影片或截圖位置為何？ | 影音內容與呈現；目前不擅自改換 |
| 素材權利（CONTENT-01） | 誰確認人物同意及素材使用權？ | 對外使用內容的範圍 |

## 7. 建議工作順序（供確認）

1. 確認本規格中的待決策項目及負責人，先處理影響收件的規則、帳號與預算。
2. 依已核准範圍建置新投稿、附件保存與管理者處理流程。
3. 串接 Drive 歸檔，完成失敗重試及資料庫、附件還原測試。
4. 通過下列驗收，並取得當次發布授權後，再開放正式共用收件。
5. 音樂史資料逐步導入共用資料庫，依實際需求另訂範圍。

這個順序是工作建議，不是時程或費用承諾。尚未授權建立外部／付費服務、變更權限、合併或部署。

## 8. 如何判斷完成

| 驗收情境 | 通過條件 | 目前證據／狀態 |
| --- | --- | --- |
| 手機閱讀 | 指定尺寸照片比例正常、無不當橫向溢出、導覽及彈窗可用 | 既有紀錄涵蓋 360／390／430／1280px 瀏覽器尺寸；實體手機待測 |
| 原有互動 | 文字收合、排序、附件數量及影音符合第 3 節 | 既有腳本涵蓋部分規則；完整操作及真實影音仍需驗收 |
| 跨裝置投稿 | 裝置 A 投稿後，管理者在裝置 B 可依權限讀取 | 後端未實作，未通過 |
| 私有待審 | 未授權訪客無法取得待審文字與附件，即使持有附件連結亦受限制 | 未實測 |
| 核准公開 | 若採先審後公開，核准前不可公開，核准後其他訪客可看到 | 規則待確認，未實測 |
| 失敗處理 | 收件失敗不誤報成功；歸檔失敗可重試且不重複建檔 | 未實測 |
| 備份還原 | 從備份成功還原文字資料及附件，留存步驟與結果 | 未實測 |
| 發布 | 取得授權後，確認發布結果及兩個公開入口可正常使用 | 本次未發布，未檢查線上畫面 |

自動檢查通過只代表檢查範圍內符合規則，不代表全部畫面、影音、權限與正式收件都已通過。
